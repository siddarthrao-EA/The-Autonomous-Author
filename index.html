01 Client Brief

Tessellate Networks — the anchor client.

The Autonomous Author is a documentation pipeline for Tessellate Networks. It reads a merged pull request or a feature spec, writes a first draft as a DITA 1.3 topic and an MDX page, checks it against the house style, and then stops. A writer reviews the draft in the app, and a code owner approves it in Git. Nothing publishes on its own, and the record shows who decided what.

Tessellate Networks builds data-center switching: the TN-7300 series of leaf switches and TessOS, the network operating system that runs on them. TessOS ships a feature release every quarter. Each release adds fabric features such as EVPN with VXLAN, and each feature needs a configuration task, a concept topic, and a CLI reference entry before customers can use it.

The documentation team has nine writers and a director. Their source is a DITA 1.3 corpus [7] authored in Oxygen and published as WebHelp [10]. A developer portal on Docusaurus is in pilot, so new content also needs an MDX version [9]. The team uses a house style based on the Google developer documentation style guide [11].

The team is not short of skill. It is short of time at the start of each feature. Writers learn about a feature when a documentation ticket arrives, often days after the code merged, and then spend days collecting context from engineers who have moved on to the next sprint. Leadership has approved an AI drafting pilot on one condition: the team must be able to show, for every published topic, which person reviewed and approved it.

03 Problem Statement

Knowledge sits in pull requests, tickets and engineers' heads. Docs arrive after the customer needs them.

Problem statement
Tessellate's writers start each feature days after the code merges, rebuild context by hand, and catch style and precision problems late, in review. The result is documentation that lands after GA. Any AI that speeds this up must leave a clear record of the human decisions, or the team cannot trust what it publishes.

06 User Stories

Eight stories. Each has acceptance criteria that the evaluation harness or the pull request can check.

US-01 · Anika · P1
As a release writer, I want to paste a merged pull request and get a DITA task topic and an MDX page, so that I start from a grounded draft on the day the code lands.
Accept when: both files validate (DITA-OT and the Docusaurus build pass); every command in the draft appears in the PR or is marked [REQUIRES INPUT]; a reasoning card exists for each agent.
US-02 · Anika · P1
As a release writer, I want an update mode for an existing topic, so that a new optional parameter changes only the steps it affects.
Accept when: the output is a diff against the existing topic; unchanged elements keep their IDs, so conrefs and keys still resolve.
US-03 · Anika · P1
As a writer, I want to run only the compliance check on a legacy topic, so that I can clean up old content without generating anything new.
Accept when: every violation cites a rule ID, an excerpt and a suggested fix; no text is rewritten until I accept a fix.
US-04 · Tomás · P2
As a spec author, I want vague quantifiers, undefined terms and missing failure paths flagged, so that engineering builds from exact requirements.
Accept when: seeded vague terms are flagged at ≥88% recall on the P2 fixtures; HIGH flags block export until I resolve them or dismiss them with a reason.
US-05 · Tomás · P2
As a spec author, I want the draft to leave a visible placeholder when it lacks a fact, so that nothing in the spec is guessed.
Accept when: every detected context gap becomes exactly one [REQUIRES INPUT: reason] placeholder; placeholder fidelity on fixtures is 1.00.
US-06 · Ravi · gate 2
As the code owner for routing docs, I want the pull request to show what the AI drafted and what the writer changed, so that I review the substance and not the wording.
Accept when: the PR includes the run log; the PR description lists the writer's decisions on every HIGH item; merge is blocked until a code owner approves.
US-07 · Helen · rules
As the owner of the house style, I want one rule change to update both the in-app check and the CI check, so that writers never see two different verdicts.
Accept when: each rule in rules.json maps to one Vale rule with the same ID; a rule without positive and negative fixtures fails CI.
US-08 · Sam · release
As the release manager, I want to see which features in a release have no approved topic, so that docs gaps are visible before GA.
Accept when: open documentation PRs carry a release label, and the list of unmerged ones serves as the gap report.

07 Proposed Design

Six agents draft and check. Two human gates decide. Git keeps the record.

Design principles

PrincipleWhat it rules out

P-4 · Gaps stay visibleA draft that fills a missing fact with a plausible guess

Why the run log goes into Git
Each approved run commits a small JSON file to .taa/runs/ on the same branch as the topic. It holds the reasoning cards and every HumanDecision. The record therefore travels with the content, survives a cleared browser, and reaches the code owner without a separate tool. A CI job fails the pull request if any HIGH flag in the log has no decision.

Compliance runs in three passes. Pattern rules (for example, Latin abbreviations) run as regular expressions in the browser with no model call. Structural rules check that required elements exist: a task needs a prereq, steps and a result. Only the remaining semantic rules, such as passive voice in long sentences, go to the model.

Outputs: one draft, two formats

The Draft Agent never writes XML or MDX. It writes a structured DraftDocument, and two small emitters turn that into files. This keeps both outputs in step, lets the emitters be unit-tested like any code, and means a schema error can never come from the model. The DITA topic stays the source of truth because Tessellate's corpus, keys and conrefs already live in DITA, and DITA-OT supports DITA 1.3 [8].

Docs-as-code gate

The writer downloads the approved files and the run log, commits them to a branch, and opens the pull request with the generated description. The app holds no Git credentials (ADR-09). GitHub requests review from the code owners of the changed paths, and with "Require review from Code Owners" turned on in branch protection, the pull request cannot merge until a code owner approves [14].

# .github/CODEOWNERS /topics/routing/ @tessellate/routing-sme /docs/routing/ @tessellate/routing-sme /rules/ @hmarsh /prompts/ @tessellate/docs-tools # .github/workflows/docs-ci.yml (jobs on every pull request) vale lint topics/ and docs/ with the Tessellate style (same rule IDs as rules.json) dita validate the map and topics with DITA-OT portal build the Docusaurus site from docs/ links check internal keys and external links run-log fail if a HIGH flag in .taa/runs/*.json has no human decision

Vale is an open-source prose linter that runs in CI [13]. The Tessellate package starts from the community implementation of the Google developer documentation style guide [11][12] and adds Tessellate's own rules. Each Vale rule carries the same ID as its entry in rules.json, so a writer sees the same verdict in the app and in CI.

10 Architecture Decision Records

Ten decisions, each with the alternative we rejected. ADR-07 to ADR-10 are new in version 2.

ADR-01Client-side app, no backendkept from v1
Decision: The app runs in the browser. Document content goes only to the model API, with the writer's key, during a run.
Rejected: A hosted backend that proxies model calls. It would receive Tessellate's unreleased feature content and need its own security review.
Trade-off: No server-side rate limiting or logging. The run log in Git replaces server logs.
ADR-02Groq behind a provider adapterrevised
Decision: Start on llama-3.3-70b-versatile on Groq [17], called through a thin adapter, so the model can change behind the promotion gate.
Rejected: Hard-coding one model. Version 1 named a model ID that Groq no longer lists.
Trade-off: The adapter is one more module to test. It costs little compared with a rewrite when a model is retired.
ADR-03Six single-purpose agents, not one large promptkept
Decision: Each agent has one job, one input schema and one output schema.
Rejected: One call that does everything. Its reasoning card could only say "I did everything", and the writer loses the stage-by-stage explanation.
Trade-off: Five or six calls per run instead of one. At current Groq speeds this adds seconds, not minutes.
ADR-04Versioned rules file, not retrieval over the style guidekept
Decision: About 80 high-impact rules as structured JSON, each with an ID, a check type and fixtures.
Rejected: Retrieval over the whole style guide. Approximate matches produce citations a writer cannot trust.
Trade-off: The rules cover a disclosed subset. Judgment calls stay with the writer.
ADR-05Fixed graph, not an autonomous agent loopkept
Decision: Every run visits the same stages in the same order.
Rejected: Letting the model choose its next tool. It could decide a draft is clean and skip compliance.
Trade-off: Less flexible. For a process with mandatory checks, that is the point.
ADR-06Ambiguity Detector as a separate critickept
Decision: A second call, prompted only to find vague terms and missing failure paths in a draft it did not write.
Rejected: Asking the Draft Agent to check its own work. Writers and models both defend what they just produced.
Trade-off: One extra call per P2 run.
ADR-07One structured draft, two emitters (DITA 1.3 and MDX)new
Decision: The model writes a JSON DraftDocument. Code turns it into a DITA task, concept or reference, and into an MDX page.
Rejected: Asking the model for XML directly, or converting DITA to MDX after the fact. The first risks invalid markup from the model; the second makes MDX a lossy copy.
Trade-off: The emitters need maintenance when topic types grow. DITA stays the source of truth, written in 1.3 because DITA 2.0 is not yet final.
ADR-08Same rule IDs in the app and in Valenew
Decision: Every pattern and structural rule exists twice under one ID: once in rules.json for the app, once as a Vale rule for CI.
Rejected: Checking only in the app. A writer could edit after export and reintroduce a violation that nothing catches.
Trade-off: Two implementations per rule. A CI job compares the ID lists so they cannot drift apart.
ADR-09The writer opens the pull request; the app holds no Git credentialsnew
Decision: The app produces the files, the run log and a ready-made PR description. The writer commits and opens the PR.
Rejected: Storing a GitHub token in the browser so the app can push. That widens the credential risk from a model key to repository write access.
Trade-off: One manual step for the writer. It is also a deliberate moment of ownership.
ADR-10Two gates: writer in the app, code owner in Gitnew
Decision: Gate 1 locks export until every HIGH flag has a decision. Gate 2 uses CODEOWNERS with required review, so merge needs a subject-matter approval [14].
Rejected: A single in-app approval. It proves the writer looked, but not that someone who knows the feature agreed.
Trade-off: SMEs review every AI-drafted topic. Section 11 explains why that review gets shorter, not longer.

11 Objection Handling

The questions a principal engineer, a docs director and a security reviewer will ask.

"Isn't this replacing writers with AI?"
No content can publish without two human approvals, and the writer is named on every run. The pipeline removes the blank page and the context chase. Judgment about what the reader needs, and the decision to approve, stay with people. The capacity it returns (Section 5) goes to review, specs and field requests.
"LLMs invent commands. Why trust a drafted procedure?"
The Draft Agent may only use facts that the Research Agent tied to a source span in the PR, spec or an answer from a named person. Anything else becomes [REQUIRES INPUT], and export stays locked until a human resolves it. The evaluation harness treats a single guessed fact as a failed release (D5).
"Self-reported confidence is unreliable."
Agreed, so the UI labels it "agent-estimated" and does not gate on it. The useful part of the card is the list of specific uncertainties. Confidence only orders the writer's attention, and the two human gates do the protecting.
"Eighty rules is a fraction of the style guide."
The rules are the subset that can be checked reliably. A check that raises false alarms teaches writers to ignore it, so the false-positive rate is a blocking gate (D3). The scope is published in the app, and the rest of the guide stays a matter of editorial judgment.
"Won't code owners now have twice the review load?"
They already review these topics. The difference is what reaches them: wording problems are fixed at gate 1, open questions arrive as explicit questions, and the PR description lists the writer's decisions. The target in Section 9 is one review round instead of about two.
"Fifty fixtures is too small an evaluation set."
The fixtures are a specification test, not a statistical sample. Each one covers a rule category or a known failure mode. New failure modes found in real runs become new fixtures, and the run logs in Git show drift that fixtures miss.
"An API key in the browser is a security risk."
The key is limited to model inference, kept in session storage by default, and the Content Security Policy only allows connections to the model API. The app holds no Git credentials at all (ADR-09). The alternative, a backend, would hold unreleased product content, which is the larger risk for Tessellate.
"Why not use a general chat assistant?"
A chat assistant can draft text. It does not know Tessellate's topic types, does not check the house rules with citations, does not emit valid DITA, and leaves no record of who approved what. Those four gaps are the scope of this design.
